Architecture: start here

This repository is a test automation platform for a new web application. Tests compose browser, API, database and emulator capabilities around one explicitly owned test scope. Application-specific pages, contracts, workflows and assertions sit above those capabilities. SampleApp and the public date-picker journeys demonstrate the boundaries; they are not your future application's business implementation.

The design is a modular library architecture with ports and adapters at change-prone boundaries. It runs as a test process calling libraries directly. Selenium, HTTP transports, EF providers and reporting clients adapt those libraries to external systems. A dependency-injection container is optional.

Central design rule

A test owns its resources; adapters own technical mechanics; scenarios own business intent. For example, TestScope owns browser lifetime, BrowserWait checks readiness, MonthNavigator reaches a month, GlobalSqaPage selects the iframe, and GSQ-01 asserts the leap-day outcome.

UI, API and database channels observe different aspects of an application. Each is optional. A calendar test needs only UI access. An API test may never start a browser. A database assertion requires the application's schema and connection. Libraries do not automatically connect an application to an emulator or database.

Preserved ideas and deliberate changes

The original framework separated generated API families, page objects, reusable steps, settings and database helpers. This starter retains those ideas, explicit Selenium waits, API generation, HTTP fault emulation, admin settings/benchmarks and integrations. It replaces mutable global registries and cross-test browser reuse with explicit ownership. It replaces business contracts/workflows with neutral examples; the extraction report records the differences.

The calendar addition extends the same architecture. Its NUnit fixture and console runner invoke one scenario catalog using the existing TestScope, BrowserFactory, BrowserSessions, BrowserWait and diagnostics.

Practical limits

TestScope constructs the default browser factory, token provider and local publisher; it is not fully configurable through constructor interfaces. An alternate composition root can supply different implementations directly. Automation.Testing references NUnit, so the console runner avoids NUnit discovery but still transitively references the package. CalendarPage navigates in its constructor, a pragmatic page-adapter choice with an observable side effect. The documentation describes these compromises rather than claiming perfect architectural purity.

Deployment view

Locally, the test process starts ChromeDriver and Chrome through Selenium. With Grid, the node owns the browser and must reach the application and emulator. Localhost inside a container refers to that container. Enable managed downloads on a Grid node and retrieve them using Downloads.FetchRemote.

Default sample tests own their local sample server. Calendar tests use the four explicit URLs in SitePages.cs. SQLite is sufficient for local database examples; PostgreSQL, Grid and MailHog are optional. WireMock runs in-process on a random port. No production application, reporting account or scheduler is provisioned.

Combining features in a business journey

This is an extension design for your new app, not a claim that SampleApp implements one complete browser/API/database system.

  1. Load settings and create a TestScope.
  2. Start an owned emulator. Configure the application's upstream endpoint through its supported test configuration.
  3. Create an entity using a generated client constructed from scope.ApiHttp. Register deletion immediately after successful creation.
  4. Use a page object for the user operation. Wait for a meaningful application state change.
  5. Observe the result using the API, an eventual database read, or an emulator journal. Correlate by the entity ID from setup.
  6. Verify a downloaded document or uniquely addressed email when relevant.
  7. Capture failure evidence, compensate in reverse order, dispose drivers/clients and write the local result.

These steps are coordinated assertions, not a distributed transaction. Rolling back a test's DB transaction does not undo an API call or the application's separate transaction. Cleanup compensates only for resources the test owns. Cleanup failures remain visible.

Configuration boundaries

Precedence is defaults, shared JSON, environment-specific JSON, local JSON, then AUTOMATION_ environment variables. Nested keys use double underscores, such as AUTOMATION_Browser__Headless. AUTOMATION_ENVIRONMENT defaults to local. NUnit loads from its output directory; DatePickerRunner loads from the current working directory.

Web/API base URLs are separate and end in a slash to preserve relative base paths. OAuth has its own endpoint. An API token does not sign in a browser and a browser session does not authenticate an API client; implement each session setup explicitly.

Parallelism

Independent scopes support isolated execution, but concurrency belongs to the runner. Never share a driver, EF context, page object or TestData random instance between simultaneous tests. A synchronized cleanup stack does not make every scope service thread-safe.

Public calendar cases are sequential with fresh cookies and browser state per case. They are optional external checks. Private suites can be partitioned by category and available Grid capacity, using owned data and cleanup. No distributed scheduler, concurrent load engine or cross-machine browser pool is included.

Low-level design

The diagrams show implemented classes and ordering. Simplified UML omits some properties and generic constraints; source code is authoritative.

Scope and lifecycle

AutomationTest creates TestScope during SetUp. InstancePerTestCase prevents fixture-field leakage. Reqnroll's ItemSteps creates its scope in BeforeScenario; the console runner constructs one directly. Scope creation validates settings, creates artifacts, records the data seed and composes HTTP/authentication. BrowserSessions is lazy: no browser starts until Current or Start is used.

CompleteAsync captures PNG/HTML on UI failure before disposal. Capture attempts are guarded individually. DisposeAsync attempts data cleanup and browser cleanup independently, disposes HTTP/token clients, and aggregates cleanup failures. Completion writes result.json, marking cleanup failure as Failed. NUnit attaches top-level files; DatePickerRunner also persists aggregate results after each case.

CleanupScope stores named asynchronous callbacks in a LIFO stack. Disposal snapshots work and memoizes the disposal task, so repeated disposal does not repeat compensation. Each callback has a 30-second deadline; a failed callback does not stop the others. Callbacks must honor cancellation: an uncooperative callback can continue after the wait times out. Total cleanup time can be the number of callbacks multiplied by their deadlines.

Selenium readiness

BrowserFactory configures Chrome/Edge/Firefox or Grid, downloads, command/page-load timeouts and window size. Implicit wait is zero. BrowserSessions owns all drivers created within a test and attempts to dispose every driver, even after another close fails.

Until creates an explicit WebDriverWait using configured timeout/polling. Only missing and stale element exceptions are ignored. Invalid selectors and other programming errors surface. Public calendar adapters wait on widget headers/values, not global network-idle on advertising-heavy pages.

DomMonthCalendar.MoveMonth computes the expected next month, clicks once and waits for that exact header. MonthNavigator rejects distances over 120 months before any click, verifies exactly one month per transition and checks a two-minute budget between steps. An in-progress WebDriver command can extend the wall-clock total. ClickDay requires the displayed target month. Date cells include a full-date identifier or a month/year-qualified locator.

API generation and transport

ApiGenerator reads PascalCase service names and local specs from contracts/services.json. Names must be unique and resolved paths must stay inside contracts. All services are generated in memory before writing files: contract failures preserve previous generated files. Final multi-file writes are not an atomic filesystem transaction. Removing a service from the manifest does not delete its old generated file; remove obsolete files explicitly.

NSwag emits a namespace, interface, client and DTOs for each service. Clients accept HttpClient, use its base address and do not own disposal. The same client can call a real server, SampleApp, WireMock or an in-memory request-capture handler. Change contracts or add wrappers/partial extensions instead of editing .g.cs files.

The handler order is HttpAuditHandler -> ReadRetryHandler -> BearerHandler -> transport. Audit records the final logical outcome and elapsed time; it is outside retry and does not log every attempt. Bearer acquisition runs per attempt. Default redirects are disabled.

GET/HEAD without content may retry three times after the first attempt on transport failure or 408/429/500/502/503/504. Retried responses are disposed. Retry-After is clamped to 0..30 seconds; otherwise bounded exponential delay and jitter apply. HttpClient timeout is 60 seconds; cancellation propagates. POST/PUT/PATCH/DELETE are not automatically replayed.

ClientCredentialsTokenProvider serializes cache access/acquisition with SemaphoreSlim and refreshes ahead of expiry using a margin up to 60 seconds. OAuth requires HTTPS outside loopback. NoTokenProvider and StaticTokenProvider share ITokenProvider. Caches belong to the scope. There is no automatic 401 refresh-and-replay policy.

Database

Repository implements distinct read/write interfaces and creates a disposable EF context per operation. Reads use AsNoTracking. WaitForAsync creates a fresh context every poll to avoid stale tracked values. Predicates are EF expressions; correlate by an owned resource ID.

Repository writes require its allowWrites constructor flag. This is a framework guard, not database authorization. DatabaseTransaction is separate and does not consult this flag. It uses the provider execution strategy, creates a context and transaction, invokes the delegate, saves, then rolls back by default or commits when explicitly requested. The delegate may be re-executed by the provider: keep HTTP/email side effects out of it.

ExampleDbContext maps SampleRecord to automation_records. Scaffold/design entities for your new schema. SQLite checks do not validate PostgreSQL-specific types, collation or transaction behavior. No production migration runs automatically.

Emulators

HttpEmulator owns a random-port WireMock server. Stub returns a mapping ID; journal queries filter by mapping. Sequence uses unique scenario state and retains its last response. WaitForRequestsAsync checks a minimum count; use Requests with an exact-count assertion when duplicates matter. AssertNoRequestsAsync observes the entire requested window rather than checking one instantaneous empty journal.

RequestCapture invokes a generated operation with an in-memory transport and captures exactly one method/path/query/body. Supply a response compatible with that operation's return type. It rejects multiple sends. Captured body/query are not automatically used by Stub, which matches method/path only; add richer mappings for those contracts.

AdminEmulatorClient is a separate settings/benchmarks control adapter. Owned helpers register deletion after successful creation. Names must be unique: deleting a shared overwritten setting is not restoration. SampleApp implements this neutral contract but does not simulate original business transaction rules.

Supporting capabilities

DataFlow executes named setup steps in sequence with the cleanup owner and cancellation. TestData records a seed for choices and uses GUIDs for unique names; the seed does not reproduce GUIDs. PerformanceProbe measures sequential latency, not concurrent load.

Downloads waits for the expected filename, no partial-file suffix, exclusive access and stable size. Grid downloads use Selenium's managed-download API. PDF text extraction is separate from browser mechanics; OCR is not supplied.

MailHog queries should use unique recipient/subject criteria. TestRail, Zephyr Enterprise and webhook publishers require explicit composition; default scope output is local JSON. Jira status and scheduler clients require your endpoint/contracts. These are supplied adapters, not automatically configured live integrations.

Architecture decisions

These records explain the starter's choices. They are decisions made for this extraction and its examples, not claims that every original class followed the same rules.

ADR-01: Modular libraries with an explicit composition root

Context: UI, API, database and emulator code change for different reasons. The original framework mixed some helpers with global state and runner concerns.

Decision: Keep technical capabilities in separate libraries and compose them per test in TestScope. Use constructor injection at transport/provider boundaries.

Why: A new app can adopt only the capabilities it needs. Ownership is visible and collaborators can be replaced in focused tests.

Alternatives considered: One large base-test class makes dependencies implicit. A DI container would provide richer registration but adds indirection to a small starter.

Cost: TestScope currently chooses concrete defaults. It must be edited or replaced to inject a custom browser factory/publisher. If composition grows, introduce a scope factory before introducing service location.

ADR-02: Fresh browser state per test

Context: Reusing a browser can preserve cookies, local storage, service workers, tabs and account state.

Decision: BrowserSessions owns multiple sessions only within one test; a new test starts fresh.

Why: Isolation is easier to reason about than incomplete reset logic.

Cost: Startup is slower. Use Grid capacity and test partitioning to scale; do not add pooling without an explicit, verified reset contract.

ADR-03: Observe conditions; execute mutations once

Context: Rendering is asynchronous and a timeout after a submission does not prove the submission failed.

Decision: Poll readiness with explicit deadlines. Re-find stale elements. Perform a click once. Retry only bodyless HTTP GET/HEAD under a bounded transient-error policy.

Why: This handles eventual state without duplicating writes. Calendar navigation separately verifies each month transition.

Cost: A late overlay can still intercept a click after readiness. Capture the failure and fix the readiness signal rather than globally retrying clicks.

ADR-04: Generate SDKs from versioned contracts

Context: Copying old generated service families would bring old business DTOs, endpoints and toolchains.

Decision: Use pinned NSwag, a multi-service manifest, generated interfaces and injected HttpClient. Keep generated code isolated.

Why: The new app supplies its own OpenAPI contracts. The transport can be authenticated, logged, emulated or captured independently.

Cost: This is not source/binary compatibility with the original Swagger/Refit clients. Generator upgrades can change signatures; review diffs and run contract checks. OpenAPI dialect compatibility must match the pinned generator.

ADR-05: Short-lived EF contexts and rollback by default

Context: Tracked entities and shared DbContexts cause stale reads and concurrency problems.

Decision: Create a context per operation/poll; expose separate read/write interfaces; make transaction commit explicit.

Why: Observations see fresh database state and context lifetime is clear.

Cost: More context creation. SQLite tests do not replace PostgreSQL integration checks. The transaction helper's direct write capability is independent of repository allowWrites.

ADR-06: Two distinct emulator mechanisms

Context: HTTP fault simulation and application-emulator administration solve different problems.

Decision: Keep owned WireMock servers and an IEmulatorAdmin HTTP client separate.

Why: WireMock tests protocol responses and journals. Admin settings/benchmarks configure a separate service contract. Combining them into one interface would imply unsupported substitutability.

Cost: The new application must be wired to its chosen upstream simulator. The sample admin contract is an example, not a copied business emulator.

ADR-07: Share the smallest calendar capability

Context: Lastest has range-specific rules and disabled weekends; GlobalSQA uses iframes; Practice uses a different popup; UK uses Flatpickr date/time/range widgets.

Decision: Share only IMonthCalendar, bounded MonthNavigator and DomMonthCalendar transition mechanics. Keep range, text entry, reset, iframe and time methods on site pages.

Why: A single enormous IDatePicker would force widgets to fake unsupported capabilities. Full-date selectors prevent adjacent-month ambiguity.

Cost: Four adapters remain. Site changes still require maintenance. Month headers use observed English locale; new locales need explicit parsing/formatting.

ADR-08: One scenario implementation, two execution front ends

Context: The workstation's NUnit adapter failed loading the earlier test assemblies before discovery.

Decision: Put the 19 scenario bodies in DatePickerScenarios. NUnit and DatePickerRunner both call them; the runner also performs eight local algorithm checks.

Why: Real Selenium behavior can be validated independently of discovery, without duplicating test logic.

Cost: The console runner is not a substitute for NUnit discovery, selection, reporting or CI validation. It still references Automation.Testing and transitively NUnit. It is deliberately sequential.

ADR-09: Public-site cases are opt-in

Context: Availability, advertising, consent and markup of external demos are outside this repository's control.

Decision: NUnit requires AUTOMATION_LIVE_DATEPICKERS=1. The runner requires --live. The manual workflow runs the runner and uploads results.

Why: Local framework checks should remain usable without four public websites. An external failure is preserved as a failure, never silently converted into a passing/ignored assertion.

Cost: Live-site coverage must be scheduled or invoked deliberately by the adopting team. Passing sample tests says nothing about your new app.

ADR-10: Documentation is delivered in source and rendered forms

Decision: Ship Markdown, editable Mermaid UML, standalone SVG diagrams and an offline HTML handbook. Keep explanations tied to actual class names and include limits beside each mechanism.

Why: Reviewers can read the design without installing a renderer and developers can evolve diagrams with code.

Cost: Visual assets and diagram source must change together. The handbook builder renders the checked-in SVGs; it does not interpret Mermaid or prove diagram/source equivalence.

SOLID and software engineering in concrete code

SOLID is used to make changes local and dependencies visible. It is not a claim that every type needs an interface or that inheritance is always wrong.

TestScope deliberately has several collaborators because composition is its responsibility. It is not a dumping ground for new-app business helpers. Site pages contain Expect methods in these examples, mixing page operations and observable postconditions for readability; larger suites may separate assertion objects without changing the navigation contract.

Open/closed

New token providers can implement ITokenProvider and be used by ApiClientFactory. A custom browser factory can implement IBrowserFactory and be passed to BrowserSessions. A new calendar implementation can implement IMonthCalendar and reuse MonthNavigator without changing its algorithm. Generated service additions use manifest entries.

This does not make every extension edit-free: TestScope has a concrete authentication-mode switch and constructs BrowserFactory. Adding a default auth mode requires composition/settings changes. Extensibility is placed at useful seams rather than promised universally.

Liskov substitution

An IMonthCalendar implementation must report the first day of the currently visible month; MoveMonth(-1/+1) must finish at exactly the adjacent month or fail; ClickDay must select an available day in the displayed month or fail. It must not silently choose an adjacent-month duplicate or set a hidden model value.

DomMonthCalendar implements that contract through WebDriver and condition waits. The local FakeCalendar validates traversal, no-op behavior, budget rejection, stuck movement and overshoot detection. It is a test double for the navigation algorithm, not proof of website correctness.

A disabled date may throw through readiness timeout; the interface does not promise every civil date is selectable. Range selection and time editing are therefore separate site capabilities. Substitution is a behavioral contract and needs tests; merely implementing an interface is insufficient.

Interface segregation

IReadRepository and IWriteRepository let read-only consumers avoid a write API. IElementWait exposes common element conditions without all concrete wait extensions. IMonthCalendar does not impose text-entry, reset, range or timezone methods. IHttpEmulator and IEmulatorAdmin remain distinct because they represent different services.

A useful interface is one a consumer needs. Avoid an interface for every DTO or a giant IFramework that exposes all tools.

Dependency inversion

High-level helpers receive transport/provider abstractions: HttpClient, HttpMessageHandler, ITokenProvider, IDbContextFactory, IWebDriver and IBrowserFactory. MonthNavigator depends on IMonthCalendar, not CSS or Selenium. Generated clients accept HttpClient instead of finding a global singleton.

The composition root selects concrete implementations. The page adapters still use concrete BrowserWait, and TestScope uses concrete local result publishing. These are practical limits; introduce further ports when a real substitution need appears.

Failure semantics

Assertions and infrastructure failures are not converted to success. Missing widgets produce timeouts with the locator/expected condition. Invalid selectors surface immediately. External site consent is handled through normal controls; overlays are not removed by script. No CAPTCHA or browser security interstitial is bypassed.

HTTP retries and state polling differ: retry repeats a read request; polling repeats an observation until a predicate holds. Replaying a write is not a polling strategy. Register compensation only after success, and use unique names so teardown removes only owned resources.

What this architecture does not prove

The starter is not a full domain-driven design, CQRS/event-sourcing implementation or microservice platform. It does not establish browser compatibility merely by offering three driver factories. It does not prove production database behavior with SQLite. It does not make public websites deterministic. These boundaries keep the claims reviewable.

Date-picker design and runbook

The suite contains 19 complex UI scenarios on the four requested public sites. It is an example of extending this starter with reusable components, not a replacement for testing your application's own calendar rules.

Run locally

Run from the extracted repository root. The console route executes exactly the same scenario bodies as NUnit and avoids the workstation's earlier test-discovery problem.


dotnet restore WebAutomation.sln --locked-mode --configfile NuGet.Config
dotnet build WebAutomation.sln -c Release --no-restore
dotnet run --project tools/DatePickerRunner -c Release --no-build -- --self-test
dotnet run --project tools/DatePickerRunner -c Release --no-build -- --list
dotnet run --project tools/DatePickerRunner -c Release --no-build -- --live

The local self-test performs eight checks without a browser or network. Live execution requires an installed browser, driver resolution and access to the four sites. Default browser is headless Chrome.


dotnet run --project tools/DatePickerRunner -c Release --no-build -- --live --site globalsqa
dotnet run --project tools/DatePickerRunner -c Release --no-build -- --live --case UK-05 --headful
dotnet run --project tools/DatePickerRunner -c Release --no-build -- --live --output artifacts/my-calendar-run

Site names are lastest, globalsqa, practice and uk. Unknown options and zero-match selections fail clearly. --live is required; invoking the runner with no arguments only prints usage. Each case creates its own scope/browser and the runner executes sequentially. Exit code is zero only when all selected cases pass.

For NUnit:


$env:AUTOMATION_LIVE_DATEPICKERS = '1'
dotnet test tests/Automation.DatePickers -c Release --filter 'TestCategory=DatePicker' --logger trx
Remove-Item Env:AUTOMATION_LIVE_DATEPICKERS

The manual GitHub Actions workflow, public-datepickers.yml, invokes the console runner and uploads its artifacts. It has not been dispatched remotely during preparation.

Component architecture

  • CalendarDates handles civil dates, leap years, ISO/English formatting and month arithmetic.
  • IMonthCalendar exposes only the displayed month, one-month movement and day selection.
  • MonthNavigator validates distance and progress, independently of Selenium.
  • DomMonthCalendar implements the transition contract using the existing BrowserWait.
  • CalendarPage holds the browser, waits and value assertions; four site pages supply selectors and site-specific operations.
  • Scenarios.All contains the 19 shared case bodies.
  • Automation.DatePickers adapts the catalog to NUnit; DatePickerRunner adapts it to a standalone executable.

No page uses a private widget API to assign selected dates. Calendar selections use native WebDriver clicks. Time/text controls use WebDriver keyboard operations and normal blur events. Disabled and readonly attributes are preserved.

Range semantics matter

Lastest restarts check-in when the second click is earlier. Flatpickr sorts the two endpoints instead. A universal range helper that silently normalizes both sites would hide one application's actual rule. These assertions therefore live in separate scenarios.

For Lastest, night counts use DateOnly.DayNumber subtraction: weekends inside a range still count even though weekend endpoints are disabled. Equal endpoints and clicking again after a completed range are not specified by this suite.

Dates, boundaries and repeatability

Cases derive their anchor year/month from the widget header rather than assuming the workstation clock matches the page timezone. Leap tests find the next leap year using Gregorian rules; the local checks cover the non-leap century 2100. Values are formatted with invariant ISO or explicit en-US culture, avoiding the workstation's Romanian date format.

A leap day may be a disabled weekend on Lastest in a future year. LAT-01 asserts the full leap-month availability and selects that day only when allowed; otherwise it selects a weekday near month-end. Other sites test actual leap-day selection. Range endpoints on Lastest are normalized to weekdays.

The algorithm rejects targets farther than 120 months and verifies each adjacent-month move. Every UI wait remains bounded by framework settings. There are no fixed Thread.Sleep calls in the date-picker examples and no retries that convert failures into passes.

Evidence and diagnosis

Each scope stores events.jsonl, result.json, downloads and, on failure, failure.png/failure.html. The console runner writes results.json after every case, containing case ID, description, outcome, duration, relative artifact path and exception. It preserves failure and teardown errors and continues to the next isolated case.

When a case fails, inspect the screenshot and first unexpected state. Check the current iframe, consent overlay, visible popup, exact month label and expected value format before editing locators. Do not weaken the assertion to match a wrong value or replace a native click with hidden model assignment.

Browser/network access failures are reported as failed attempts, not skipped tests. Only absence of explicit live opt-in causes NUnit's intentional skip. The validation report distinguishes actual live results, local checks, compilation and the runner-loading limitation.

Coverage boundaries

These are functional examples, not exhaustive accessibility, timezone, localization, mobile or cross-browser certification. They do not automate Lastest's operating-system native date popup, submit forms, solve challenges, test invalid typed values across every widget, or load-test the sites. New application requirements should add those cases explicitly where relevant.

Implementing your new application's tests

Start with one vertical journey

Choose a small user outcome that has API setup, a UI action and an observable result. Define its contract before adding broad helper abstractions. Keep the public date-picker examples as references; put your application's pages/tests in a separate project.

  1. Extract the archive and initialize a new Git repository. Keep package locks and generated source under version control.
  2. Run restore/build and SmokeCheck. Review VALIDATION.md to separate local checks from unvalidated integrations.
  3. Configure web/API URLs and authentication using environment variables or uncommitted local settings.
  4. Add your OpenAPI file and service entry, generate the client and inspect the diff.
  5. Add a page object that accepts a driver and BrowserWait. Use stable test IDs owned by your app.
  6. Create data through the API, register cleanup immediately, perform the UI action, and verify by an explicit app signal.
  7. Add a database or emulator assertion only when it adds coverage the UI/API cannot provide.
  8. Run locally, then configure CI artifacts and explicitly selected external integrations.

A composition sketch

The following illustrates extension points; OrdersClient, OrdersPage and the Orders database belong to your future app and are not bundled types.


// Illustrative new-app code: supply the named application types.
var api = new OrdersClient(scope.ApiHttp);
var order = await api.CreateAsync(newOrder, token);
scope.Cleanup.Register($"order {order.Id}", ct => api.DeleteAsync(order.Id, ct));

    new BrowserWait(scope.Browsers.Current, scope.Settings.Wait));

    row => row.Id == order.Id && row.Status == "Submitted",
    TimeSpan.FromSeconds(20), token);

API creation and database observation use the same identifier. Do not generate a second unrelated random name for each layer. A failure after creation still triggers registered deletion.

Adding a custom calendar

For a month-grid control, implement IMonthCalendar in your app's page/component project. Report the visible month as DateOnly(year, month, 1). Move one month and wait for its header. Resolve the full target date and use BrowserWait.Click. Reuse MonthNavigator.

For a range widget, keep the range state machine at the page/scenario layer. Define whether a reversed second click sorts endpoints, restarts selection or rejects the value. Lastest and the UK site intentionally demonstrate different rules. Add time editing only for widgets that expose it.

For a native HTML date input, use browser-appropriate user input and assert both its ISO value and the application's committed response. Do not set the hidden widget model or remove readonly/disabled attributes and then claim UI coverage. The current public suite targets the custom calendars and does not promise cross-browser native-popup automation.

Integrating emulation

Start HttpEmulator, define the expected upstream response and configure your application's upstream URL. Register the emulator's disposal with the test's cleanup owner if it must outlive the scenario body. Assert the request journal after triggering the application.

RequestCapture can derive a template from a generated client operation without network traffic. Add explicit query/body matching when needed; Stub's simple overload matches method/path. Use AdminEmulatorClient only when your emulator server implements the documented settings/benchmarks contract.

Database ownership

Create application-specific entities/context and pass a context factory to Repository. Keep ordinary assertions on IReadRepository. Enable write repositories deliberately for test setup. Use DatabaseTransaction for DB-only work; its rollback cannot undo mutations sent over HTTP. Run provider-specific integration checks before relying on PostgreSQL behavior.

CI rollout

Start with restore, deterministic generation diff, build, local navigation checks, SmokeCheck and your isolated app tests. Add UI jobs with browser/Grid capacity and artifact upload. Keep the public demo workflow manual unless your team deliberately chooses a schedule. The supplied manual workflow publishes no business results to third-party reporting tools.

When adding a reporting publisher, define ownership of its HttpClient, required case IDs, failure behavior and data retention. Default TestScope output remains local JSON until you explicitly compose an external publisher.

Extension review checklist

  • Does the new helper have one clear responsibility and explicit dependencies?
  • Are waits tied to observable completion, with bounded time and clear messages?
  • Can setup create duplicate side effects after a retry?
  • Is every owned resource registered for cleanup immediately after creation?
  • Are browser, context and token lifetimes isolated appropriately?
  • Does the test assert a business result, not only the value it just assigned?
  • Are contract changes reflected in generated source and documentation?
  • Is validation evidence honest about the environment and executed cases?

API generation and services

Add an entry to contracts/services.json:


[
  { "name": "Sample", "spec": "sample.openapi.json" },
  { "name": "Identity", "spec": "identity.openapi.json" }
]

The generator reads local OpenAPI documents, validates service names and path containment, generates all clients in memory, then writes src/Automation.Generated/{Name}.g.cs. It does not download private contracts, update external docs, modify handmade files or silently delete removed-service outputs. If removing a service, remove its old .g.cs file deliberately. Review generated changes and compile clients before committing. Commit the specs, manifest, generated source and lock files together.


using var http = ApiClientFactory.Create(baseUri, tokenProvider, eventSink);
ISampleClient api = new SampleClient(http);
var item = await api.CreateItemAsync(new CreateItem { Name = "unique-name" }, token);

The generated API paths are relative and use the supplied HttpClient base address. Check whether the new specification already includes /api; avoid duplicating that path in ApiBaseUrl. Selenium waits and pages


var waits = new BrowserWait(scope.Browsers.Current, scope.Settings.Wait);
waits.Visible(By.CssSelector("[data-testid=page-ready]"));
waits.Gone(By.CssSelector("[data-testid=loading]"));
waits.Text(By.Id("status"), text => text == "Completed");
waits.Click(By.CssSelector("button[type=submit]"));

Use semantic readiness markers and application-specific loading locators. Gone can pass immediately if a loader has not appeared yet; combine it with the expected final state or track the request initiated by the action. StableList stabilizes count/text, not every possible DOM property. A clear clickability hit-test cannot guarantee an overlay will not appear between waiting and clicking; failures remain visible instead of replaying a submission.

PageComponent.Find reacquires the component root and child during polling. Add component-specific methods rather than caching IWebElements. Use BrowserActions for upload, drag/drop, new windows and frames; switch back to default content/window as part of each flow. Use Browsers.Start() and SwitchTo(index) for independent users in one test.

Selenium Grid


docker compose up -d selenium
$env:AUTOMATION_Browser__GridUrl = 'http://localhost:4444/'

Grid sessions enable managed downloads; Downloads.FetchRemote retrieves a named remote file. A local download path is meaningful only to a local driver. The optional GridCapacity helper polls /status before requesting a browser, but it does not reserve a slot. Session creation has a command timeout and relies on Grid's queue.

The bundled sample tests bind their app to 127.0.0.1 on a random port. They are local-browser examples. To test via Docker Grid, run the app separately on an interface reachable from the container and create tests using that URL (for example host.docker.internal on Docker Desktop), or deploy the app and Grid on the same Docker network. Do not pass the test runner's localhost URL to a remote browser.

Compose includes PostgreSQL and MailHog. Set POSTGRES_PASSWORD in .env before starting PostgreSQL. Services bind host ports to loopback. docker compose down stops services while keeping the database volume; deleting volumes is a separate deliberate action.

Database


var factory = DatabaseFactory.Create(settings.Database);
IReadRepository<SampleRecord> records = new Repository<ExampleDbContext, SampleRecord>(factory);
var row = await records.WaitForAsync(x => x.Id == expectedId, TimeSpan.FromSeconds(15), token);

Reads are detached and use a fresh context. IWriteRepository<T> is an explicit opt-in surface: construct the repository with allowWrites: true only where intended. DatabaseTransaction.ExecuteAsync rolls back by default; commit: true is an explicit write decision. Retried transaction delegates must contain only database work: no HTTP calls, email, or non-idempotent external effects.

For a new schema, set AUTOMATION_Database__ConnectionString and run:


./scripts/Scaffold-Database.ps1 -Schemas public,identity -ContextName ApplicationDbContext

The script creates a new timestamped Generated/Scaffold_* directory. Review/replace previous generated snapshots deliberately; retaining multiple snapshots with the same class/namespace causes duplicate types. --no-onconfiguring prevents a connection string being written to generated code, but the EF CLI receives it as a process argument. Handwritten repositories stay outside generated folders. Use Repository<ApplicationDbContext, YourEntity> with a corresponding factory. Generic repository queries replace the source's repeated per-entity generated select wrappers.

EnsureCreatedAsync is only used for disposable SQLite tests. The framework never migrates or creates your application's schema automatically. PostgreSQL execution, permissions and scaffolding must be validated against your intended test database.

Emulators and test-data flows


await using var emulator = new HttpEmulator();
var id = emulator.Stub("POST", "/webhook", 202, "{}", TimeSpan.FromMilliseconds(100));
// Configure the application under test to send this test's webhook to emulator.BaseUrl.
var requests = await emulator.WaitForRequestsAsync(id, 1, TimeSpan.FromSeconds(10));

Sequence models failure then recovery. AssertNoRequestsAsync watches for the entire observation window. RequestCapture derives a method/path/query/body template from a generated-client invocation without networking; supply a canned response compatible with its return type. Stub matches method and path only: add more advanced WireMock matching when body, header or query discrimination is required.

Use AdminEmulatorClient for the sample transaction/benchmark admin protocol. Give every setting a unique name; SetOwnedTransactionAsync assumes the caller owns that name and does not restore an existing shared setting. Do not overwrite other tests' settings. Register compensations with CleanupScope for API/database resources as soon as they exist. DataFlow executes named creation steps and leaves cleanup ownership to the surrounding scope.

Reporting, email and files

TestScope always writes a local result JSON. To publish externally, inject/configure an ITestResultPublisher in your test lifecycle and explicitly call PublishAsync after computing the final outcome. Configure authentication on that publisher's dedicated HttpClient. TestRail's base address should end in /index.php?/api/v2/; Zephyr Enterprise's base address should end in its API root /. Configure Zephyr status IDs for your instance. Scale/Squad APIs require a different adapter. Jira lookup is read-only and does not rewrite test results.

MailHog's HTTP API and SMTP service are separate endpoints. Configure your application's SMTP to the mailbox container, then poll using a unique recipient per test. The adapter returns the raw stored body; use a MIME library if your assertions require decoded multipart/quoted-printable content.

For PDF text, use IPdfTextExtractor. It does not OCR scanned pages or perform visual comparison. Local downloads wait for the final file, absence of partial suffixes, exclusive readability and stable size. Use a fresh directory or unique name to avoid matching an old file. ZIP inspection lists entries without extracting them.

CI and dependency updates

The sample GitHub Actions job runs restore in locked mode, regenerates clients, checks for drift and runs non-browser tests. It does not deploy or post results to another system. Add a separate UI job for your chosen browser/Grid setup. NUnit fixtures can opt into parallel execution once their resources and setup are isolated; per-test fixture lifecycle is supplied where mutable test fields are used.

Changes that matter when migrating

  • Swagger Codegen 2.x, hand-edited generated RestSharp code and Java-based scripts are replaced with NSwag C# generation. This preserves API generation as a capability, not binary/source compatibility with the old generated SDK. Fix specifications or add wrappers instead of restoring manual edits after generation. APIs described by OpenAPI 3.1 need compatibility review with the pinned generator.
  • Framework runtime moves from .NET 6 to .NET 8, and EF Core/provider versions are upgraded together. Business EF entities are regenerated from the new app's database; source database mappings are deliberately not renamed and reused.
  • The old application emulator is a separate server not implemented by this repository. The generic admin client and sample server preserve its control pattern, but payload shapes and routes must match your new emulator. Generic settings stored by the demo are not a financial transaction simulator.
  • WireMock's in-process .NET server is used instead of requiring a shared remote emulator. For a remote application, host an emulator reachable from that application and implement the same IHttpEmulator boundary or use WireMock's admin API. A per-test loopback URL is useful only when the caller can reach it.
  • Catch-all retry, nested waits, ignored HTTP status codes, indefinite/shared state, raw API body logging and global emulator resets are not retained.
  • The original UI library has many custom widgets tied to specific CSS/frameworks. The starter carries the page/component pattern and interaction primitives; dropdowns, grids and editors should be implemented against the new app's markup.

Deliberately excluded or requiring application-specific work

Old page selectors, API DTOs/endpoints, users, role IDs, financial/shipping workflows, fixtures/uploads, database entities, private URLs, credentials, production-like datasets, Jira/Zephyr IDs, CI tokens and trigger scripts are excluded. Only neutral examples are bundled.

The source includes an Android APK and emulator-launch batch file in upload test data. Those are application artifacts, not a portable mobile automation implementation for a new web app. They are not included. This starter's emulator features are the HTTP/WireMock and admin-service mechanisms actually used by the reviewed web/API framework.

Specialized business document generation, image/OCR comparison, vendor SDKs, application-specific performance scripts, password-grant login/impersonation and full custom-widget libraries need new-app contracts and are not advertised as complete here. PDF text extraction, core browser/file operations and timing primitives are included.
